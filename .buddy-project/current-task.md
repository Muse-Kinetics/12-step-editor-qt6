## Important fix after first hardware smoke-test (2026-07-31)

The first real console log (WMS backend, real hardware) showed the firmware file being sent as **one 88KB blob via the legacy `slotSendSysExBA` path**, chunked at 48 bytes with **no per-packet identity request/reply** — i.e. the packetized transport wasn't actually active. Root cause: `MidiDeviceManager::isPacketizedFirmwareUpdateEnabled()` in `KMI_mdm.cpp` only auto-enables the packetized handshake system for SoftStep PIDs by default; every other product must opt in explicitly via `slotSetFirmwareUpdateTransportMode(FW_TRANSPORT_PACKETIZED)`. Missed this during the original §4.5 pass — the file/`.qrc`/version-bump work was correct, but the actual transport switch was never flipped. Fixed by calling `TwelveStep->slotSetFirmwareUpdateTransportMode(FW_TRANSPORT_PACKETIZED);` right after `TwelveStep` is constructed in `mainwindow.cpp`. Rebuilt clean.

Also clarified for the record: the `48` byte chunk size seen in the log (`sysExTxChunkSizeFW`) is a *different, lower-level* setting — the MIDI-transport wire-slicing size used only by the legacy blob-send path, tied to the 64-byte USB MIDI packet limit. It has nothing to do with the `-cs512` firmware packet size. The packetized path's `sendSysExImmediate()` sends each full pre-chunked packet (up to 512 bytes) in a single `midi_out->sendMessage()` call with no further slicing — so enabling packetized mode was the complete fix; `sysExTxChunkSizeFW` did not need changing.

## Critical bug found + fixed via WinMM hardware log (2026-07-31)

First real WinMM hardware test (`12-Step-Editor-20260730-142834-485.log`) showed the firmware update appearing to hang/fail, requiring two attempts. Full trace: all 235 chunks sent successfully both times; the device's port closes as expected while it reboots bootloader→application; the app immediately tries to send a "final verification" SysEx identity request on that now-closed port, which fails (`sendSysExImmediate`'s `!port_out_open` check) — and the code sets `firmwareUpdateState = FWUD_STATE_FAIL` **without** calling `resetPacketizedFirmwareUpdate()` or clearing `packetizedFirmwarePhase`, so `isPacketizedFirmwareTransferActive()` kept returning true and something kept re-invoking the same failing attempt with no real delay. Result: a busy loop (627 failed attempts logged) lasting **3+ minutes**, only interrupted when the user gave up and retried. On the second attempt the device actually did reconnect with `FirmwareMatch` (confirming the flash genuinely succeeded both times), but the app never recognized success, so closing the stuck dialog logged `success: false` anyway. WinMM exposed this reliably because its port close→reopen during this transition took 18+ seconds in the log; WMS may reconnect fast enough to rarely hit it, but it's the same code path so isn't guaranteed safe.

**Fix in `KMI_mdm.cpp`** (uncommitted, not pushed): in both `FW_PACKET_PHASE_FINAL_DELAY` and the retry branch of `FW_PACKET_PHASE_WAIT_FINAL_VERIFY`, check `port_out_open` before attempting `sendFirmwareIdentityRequest()`. If the port isn't open, don't attempt the send or burn a retry — just reschedule the pump at a new `PACKETIZED_FW_PORT_POLL_INTERVAL_MS` (1000ms) poll interval, bounded by the existing `FW_UPDATE_TIMEOUT_INTERVAL` (90s, via `firmwareUpdateStateTimer`, already running since the last chunk was sent) — matching the generous "waiting for device to reappear" pattern already used elsewhere in this same file for the pre-chunking bootloader-entry wait. Once the port reopens, normal ACK-timeout/retry logic (3 retries × 5s, for "port open but no valid reply" cases) resumes unaffected. Rebuilt clean. **Not yet re-tested against real hardware** — the original log predates the WMS-transport-mode fix above, so this exact repro hasn't been re-run since either fix landed.

## Existing-install detection: installer now offers to remove + reinstall (2026-07-31)

User asked what happens if someone runs the new installer while an old version is still installed. Tested empirically: QtIFW's engine-level `TargetDirectoryInUse` check is a hard block (confirmed via the framework docs — it's not a real Yes/No choice, unlike `OverwriteTargetDirectory`), so the installer just errors out and refuses to proceed. Also found, while investigating, that the in-app Help → Check for Updates menu item is a **completely separate, disconnected** mechanism (`KMI_updates.cpp`, checks `files.keithmcmillen.com/.../softwareVersionCheck.json`, links to the downloads page) that has no knowledge of `maintenancetool`/GitHub Pages at all — flagged as a possible future follow-up, not undertaken this session.

Fix: `win-build/config/controller.qs` (new file) implements `Controller.prototype.TargetDirectoryPageCallback`, which fires when the Installation Folder wizard page is shown — i.e. before the native `TargetDirectoryInUse` check would otherwise block. If `maintenancetool.exe` is found at the target dir, it asks the user (Yes/No) whether to remove the existing installation, and if so runs that old install's `maintenancetool.exe purge -c --am` synchronously via `installer.execute()`, so the directory is gone before the native check ever fires. Wired in via `<ControlScript>controller.qs</ControlScript>` in `config.xml` (previously a stale, non-functional commented-out reference to a nonexistent `pre-install2.qs`). `win-build/config/pre-install.qs` (pre-existing, already dead code — defines `preInstall()`, which isn't a real QtIFW callback name) was left untouched, out of scope.

**Bug found + fixed during real hardware/GUI testing** (user ran the actual installer, not just headless CLI): the immediate post-purge `installer.fileExists(maintenanceTool)` re-check raced the purge — `maintenancetool.exe` can't delete its own running binary, so final cleanup of the last few files completes in a short-lived helper process *after* `installer.execute()` returns, and the immediate check saw stale state and reported "could not be fully removed" even though removal had actually succeeded. Fixed by adding a ~2s grace period (`ping -n 3 127.0.0.1` as a sleep substitute, since QJSEngine control scripts have no native sleep) before the re-check. **User confirmed working end-to-end** on real hardware/GUI: dialog appears, purge removes the old install, no false error, clean reinstall proceeds. Also learned along the way: `-t`/`--root` is CLI-only, not honored in GUI-mode installer runs (GUI always uses the `TargetDir` from `config.xml`).

Uncommitted on `main`, awaiting review like everything else this session: `win-build/config/controller.qs` (new), `win-build/config/config.xml` (`ControlScript` wiring).

## Decided against: wiring in-app "Check for Updates" to maintenancetool (2026-07-31)

Considered as a follow-up (see prior section) but the user decided against it: macOS has no QtIFW installer at all (DMG + notarization only), so macOS users must always go through the in-app checker → downloads-page → manual-run-installer path regardless. Keeping Windows on that same path (rather than special-casing it to use `maintenancetool`) keeps the update UX consistent across platforms. This is a reasonable call *because* the `controller.qs` existing-install fix (previous section) already makes "download and run the new installer" a smooth, self-service path on Windows even with an old version installed — the maintenancetool/GitHub Pages repo remains available for anyone who wants to invoke it directly (e.g. via the Start Menu uninstall shortcut), it's just not surfaced in the app UI. No code changes from this decision; `KMI_updates.cpp`'s downloads-page behavior stays as-is.
